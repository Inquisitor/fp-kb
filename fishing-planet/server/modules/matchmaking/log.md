# Decision Log — Matchmaking

## 2026-07-26
- The Mongo `tournamentLog` rating ledger is **not** a complete record of rating events, and the omission is systematic rather than incidental: `NewProfileRating` clamps the result at zero and the ledger write is conditional on the rating having changed, so a no-show penalty landing on a player already at PCR 0 moves nothing and emits no line at all. The negative-rating correction branch does not catch it either, because the clamp runs first. Consequence for any rating analysis: **volume comes from SQL, shape comes from the ledger** — a sparse ledger for a player sitting near zero is a logging artifact, not low activity. This retroactively explains the parser-vs-SQL divergence FP-43631 had carried as an unexplained anomaly since week-9. Full treatment in [rating application](rating-application.md)
- Corollary: a ledger line reports the assessed penalty but a clamped before/after pair, so the two disagree near the floor. Arithmetic over the delta figure overstates the drain — read the before/after pair
- A gap between assessed penalties and ledger lines has two distinct causes that must not be conflated: floor absorption (above) and application still queued because the player has not reconnected — the latter being the familiar batched-flush pattern. Discriminator: whether the window contains any line ending at 0
- Defect filed to [backlog](backlog.md): log unconditionally so the ledger stops silently dropping real events

## 2026-07-14
- Finding (FP-44965): the matchmaking grouping gate is content-only — `MatchmakingLogic.ProcessGroupingForTournament` / (old binary) `MakeGroups` groups iff `KindId == Competition && Grouping != null`. There is no env or platform flag. Consequence: on a pre-release (pre-LBM) binary where matchmaking is not launched, any competition template that carries a `Grouping` block in `Tournament(Template).ConfigJson` will still group participants. Surfaced on NX prod via a single stale template (168 "The Size Matters", old pre-rename `Groups` schema) that had grouping while the platform runs the old binary with the feature unreleased. Remediation for an unreleased platform is to strip `$.Grouping` from the offending template (and any already-generated future tournaments), not to sync content from DEV — DEV/TEST/QA intentionally carry the full new (`Brackets`) content and syncing it onto the old binary either spreads grouping or breaks on the schema mismatch.
- Operational (regenerate cutoff): `RegenerateFutureCompetitions` (`WebAdmin ToolsModel_Competitions`) calls `RemoveFutureCompetetiveActivities(Competition, now+2h)` → `DELETE FROM dbo.Tournaments WHERE RegistrationStart > now+2h AND KindId=3`, then re-randomizes from templates. The cutoff is on `RegistrationStart`, not `StartDate`. A template opens registration `RegistrationDayOffset` days + `(StartHour − RegistrationStartHour)` hours before start (12h for template 168), so the effective "won't touch" horizon is ~14h from `StartDate` (2h buffer + 12h registration window) — competitions starting within ~14h keep their rows (registration open, players may be registered), further-out ones are wiped and regenerated. Blast radius: it wipes/regenerates ALL in-window future competitions, not just a target (140 rows on NX prod), so to fix a single bad row prefer a surgical `ConfigJson` edit. No Tournament-DTO cache exists — a `ConfigJson` edit is picked up by the AsyncProcessor re-poll before `ProcessGrouping`, provided it lands >5 min before start.

## 2026-04-29
- Incident: rating-related competition feature (`Places[i].Rating`, `NoShowRatingPenalty`, `ZeroScoreRatingPenalty`, `Grouping`) shipped to Steam prod today. 7 competition Tournament rows scheduled for today/tomorrow (IDs 318866–318872) were generated by the **previous** binary and so missed all four fields in their `ConfigJson`. Standard remediation `RegenerateFutureCompetitions` skipped them because their `RegistrationStart` was already in the past (registrations existed: 506 rows / 268 distinct users). `RegenerateCompetitionsRandom` would have regenerated them but at the cost of all those registrations
- Hot-patched in place via point `JSON_MODIFY` (idempotent, values copied from each Tournament's Template):
  - All 7 (live included): `Places[i].Rating` 1..10 and root-level `NoShowRatingPenalty` / `ZeroScoreRatingPenalty`
  - 6 upcoming (live excluded): `Grouping` (whole object). Skipped on live because `ProcessGrouping` runs at tournament start — that moment was already past for live, no `BracketId`s to assign retroactively. All 6 upcoming will group correctly on their `StartDate`. Live 318866 plays as one common pool — acceptable since `RatingMultiplier=1.0` means rating math is identical, only bracket-level ranking is missing
  - Places > 10 not added — by design (penalties flow through `*RatingPenalty` now, not legacy tail places)
- `past` cohort (713) is history, not a defect — they were generated AND played under the pre-feature binary, on the contract they actually had. Nothing to patch. `far-future` cohort (142) generated after deploy, already healthy
- Lesson: any `TournamentJsonConfig` schema extension creates this exact gap — future competitions generated before deploy will be missing the new fields, and any of them with active registrations cannot be regenerated. Release procedure for such changes should include a `JSON_MODIFY`-based backfill step targeting `Tournaments` rows with `EndDate > now` whose Template defines the new fields. Without it, the only options are losing user state (cascade-delete via `RegenerateCompetitionsRandom`) or hand-patching, as we did here
- Finding (evening): the morning `Grouping` backfill via `JSON_QUERY(tt.ConfigJson, '$.Grouping')` + `JSON_MODIFY` was incomplete. Templates never store `Brackets[i].MaxRating` — it is auto-computed by `MatchmakingLogic.InitializeGrouping` during template deserialization. The two `TournamentsHelper.FromDto` overloads are asymmetric: `FromDto(TournamentTemplateDto)` calls `InitializeGrouping`, but `FromDto(TournamentDto)` (used by `TournamentStartAdapter` → `ProcessGrouping`) does not. The regular generation pipeline sidesteps this by deserializing the template first (initializes `Grouping`), then re-serializing the now-complete object into the Tournament's `ConfigJson`. Raw-template `JSON_MODIFY` copy bypasses the initializer, so `int MaxRating = 0` per bracket → `MatchmakingLogic.CreateBuckets` filters by inverted ranges and admits only `CompetitionRating == 0` participants into bracket 1 (the rest end up unassigned). [Matchmaking spec on Confluence](https://fishingplanet.atlassian.net/wiki/spaces/FP/pages/5505613835) confirms `MaxRating` is auto-computed and "do not set manually" — formalising the implicit contract this defect class breaks
- Mitigated: per-bracket `MaxRating` (100 / 1000 / 2147483647 — recomputed via `MinRating[i+1] - 1` for non-last brackets, `int.MaxValue` for the last) backfilled into the two still-upcoming competitions (318871, 318872) via point `JSON_MODIFY`, applied >5 minutes before each `StartDate`. The three already-grouped tournaments (318868 ended, 318869 ended, 318870 live) left as-is — `ProcessGrouping` already executed and `RatingMultiplier = 1.0` makes per-bracket rating math equivalent
- Lesson: code-side defensive fix is the right place for this class — invoke `MatchmakingLogic.InitializeGrouping` either inside `MatchmakingLogic.ProcessGroupingForTournament` after its early-return guard (local, closes the gap at the manifestation point) or symmetrically inside `TournamentsHelper.FromDto(TournamentDto)`, mirroring the existing `FromDto(TournamentTemplateDto)` overload (closes the gap for any future caller). Either turns the "MaxRating must be persisted in `ConfigJson`" implicit contract into a self-healing one — future template-`Grouping` `JSON_MODIFY` backfills no longer need a parallel `MaxRating` step. Strongly recommended to land before next platform deploy
