## Status

Post-release follow-ups parked in [`backlog.md`](backlog.md).

Root causes (both live-proven): **#1 reorder** - chat server dispatches ops to the ThreadPool with no inter-message ordering; adjacent Leave+re-Join of a club channel can apply Join-before-Leave → member silently dropped from `participants` (proven on Steam prod via the rapid leave+join debug trigger, `club2176`). **#2 eviction** - non-persistent club/UGC/FTG channels are evicted after 30 min of message inactivity and recreated with empty `participants`, no per-user Leave (deterministic; proven locally + Xbox `club6777`; the dominant historical cause). Sending/persistence are not membership-gated, delivery is → canonical "saved but not shown". Full forensics: [`artifacts/root-cause.md`](artifacts/root-cause.md).

## Summary

Players report that chat messages stop appearing in real time "after a while fishing": new messages (user text and system events — catches, clubmate online/offline) are not displayed, while older ones may vanish too. The messages **are persisted** (visible in the log / WebAdmin). A game restart, relog, or changing location temporarily restores delivery. Club chat is the most-affected surface; historically also room/global on Steam, Xbox, Mobile.

This is a **delivery/subscription** bug, not a persistence or ordering bug — distinct from [[FP-44478]] (club bait re-delivery + equal-timestamp message ordering), which is already fixed and does not address this.

## Mechanism (root cause — code-confirmed; live confirmation pending)

Trigger is client-side, failure is server-side. Full chain + prod-log overlay: [`artifacts/root-cause.md`](artifacts/root-cause.md).

- **Server (root):** incoming chat ops keep order into `IncomingQueue` (FIFO) but `ChatProcessor.ProcessMessage` dispatches each to the **ThreadPool** (`UseThreadPoolExecutor`, prod — `ChatApplication.cs:174`) → adjacent messages process with no ordering. Leave-then-reJoin of the same user+channel can apply Join-then-Leave → user removed from `ChatChannel.participants`. The per-channel lock guards the list, not the order.
- **Client (trigger, STR 80245):** on travel the client issues Leave + immediate re-Join of the club channel; Pond→Globe issues a *double* Leave then Join. These adjacent ops are what race.
- **Why club not global:** club Join is automatic on entering a location (adjacent to the travel Leave); global `g3` Join is triggered separately (on opening chat), not adjacent → survives. Explains "only Club chat" + "own messages don't appear" (delivery includes the sender only if he's a participant).
- **Prod evidence (Waz, club6777, 2026-06-24):** game-side sysLog shows him joined 13:09:11→16:10:05, yet his 16:04/16:08 messages (persisted in chatLog) weren't echoed to him → chat-server `participants` lacked him → the 13:09:08/13:09:11 Leave/Join pair reordered. Double-Leave seen 06-25 13:08:42/13:08:45.
- **Why prior mitigations missed it:** r13569/r13578 fix peer cleanup (r13578 is Master-side), not the chat-server reorder; client r46485 fixed client STR only.
